# V1 User Import Strategy

## Goal

Import the existing `v1` user directory into `v2` safely, without carrying over weak password hygiene or creating confusion during rollout.

## Recommended approach

Use a **staged profile import + controlled credential activation** strategy.

This means:

1. Import every user profile from `v1` into `v2`.
2. Do **not** preserve legacy passwords as-is.
3. Keep imported users inactive for login until their credential path is defined.
4. Enable access in waves:
   - pilot admins first
   - early user cohort next
   - full population later

## Why this is the best option

- `v1` passwords should not become a permanent dependency of `v2`.
- `v2` already has stricter password expectations and cleaner security boundaries.
- A staged rollout reduces support load.
- It also keeps the future Entra / Azure direction cleaner.

## Recommended credential model

### Phase 1: profile import only

Import:

- username
- first name
- last name
- display name
- email
- employee code
- department
- job title
- location
- phone
- timezone
- notes
- active organization memberships

Set:

- `is_active = true` only for platform visibility
- `login_enabled = false` conceptually until activation flow is complete

If a dedicated `login_enabled` field does not exist yet, use one of these temporary patterns:

- keep users imported but with randomized high-entropy passwords not shared with users
- or mark imported users as inactive until activation

### Phase 2: pilot activation

Activate a small set first:

- super admin
- 2 to 5 organization admins
- a small user pilot

For this group:

- assign strong temporary passwords
- require first-login password change once we add that flow

### Phase 3: broad rollout

After the pilot:

- import remaining users if not already imported
- activate by organization or cohort
- communicate credentials or reset path centrally

## Password strategy options

### Option A: temporary passwords generated by admin

Best if email automation is not ready yet.

Flow:

1. import users
2. generate strong temporary passwords
3. share credentials through trusted internal channel
4. force password rotation later

Pros:

- simple
- fast
- works with current stack

Cons:

- operationally heavier
- not ideal long term

### Option B: first-login activation / reset token

Best medium-term option before Entra integration.

Flow:

1. import users without usable passwords
2. create one-time activation token
3. user sets their own password
4. token expires

Pros:

- safer than distributing temporary passwords
- cleaner user experience

Cons:

- requires activation UI + token backend
- ideally needs email or secure delivery workflow

### Option C: wait for Entra / Azure

Best long term, not best immediate rollout path.

Pros:

- strongest future state
- avoids local password lifecycle at scale

Cons:

- blocks adoption now
- requires identity integration work first

## My recommendation

Use **Option A now**, but in a controlled staged rollout.

That means:

- import all user profiles now or very soon
- do not import legacy passwords
- generate temporary strong passwords only for the first activated cohorts
- plan Option B next
- later replace the whole credential model with Entra

## Operational rollout order

1. Import profiles and memberships from `v1`.
2. Validate imported organizations and sharing scopes.
3. Activate admins first.
4. Let admins validate:
   - login
   - room access
   - office access
   - support access
5. Activate user cohorts gradually.
6. Freeze new direct password distribution once activation/reset flow exists.

## Data to import from v1

Import:

- users
- memberships
- group associations if needed
- profile metadata

Do not import:

- active sessions
- raw session tokens
- audit noise
- legacy password behavior

## Technical note

The import script already identifies `v1` users and can support staged activation.

Before running production import, confirm:

- whether imported users should start inactive or with randomized passwords
- which first cohort should be activated
- whether admins should receive credentials manually or through a reset flow

## Decision to make next

Pick one:

1. Import all users now with randomized strong passwords and activate only pilot admins.
2. Import all users now as non-login-ready profiles and build activation next.
3. Import only the first pilot cohort now, then expand later.

## Recommended next step

Choose **1** if speed matters most.
Choose **2** if rollout quality and security hygiene matter most.

If no other constraint exists, I recommend **2** as the cleanest product decision.
